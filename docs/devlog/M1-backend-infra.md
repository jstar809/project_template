# M1. 백엔드 공통 인프라

> 작성일: 2026-09-16 · 소요 시간: 약 1.5시간 · 관련 요구사항: PRD 8장(FR-ARCH), 9.8(FR-INFRA), 11장(데이터 모델)

## 1. 이번 단계의 목표

기능(회원가입, 게시판)을 만들기 전에 **모든 기능이 공통으로 쓸 바닥**을 깐다. 이 단계가 끝나면 다음이 가능해진다.

- 두 DB(PostgreSQL, MySQL)에 같은 스키마가 생기고, 애플리케이션이 스키마와 엔티티가 맞는지 검증한다.
- 조회는 MyBatis, 쓰기는 JPA로 나눠 쓸 준비가 된다. DB마다 다른 SQL도 분기할 수 있다.
- 에러가 나면 언제나 같은 형식(ProblemDetail + code + traceId)으로 응답한다.
- 아키텍처 규칙을 어긴 코드를 테스트가 자동으로 잡는다.
- 스케줄러, 캐시, 파일 저장, 호출 제한의 뼈대가 준비된다.

## 2. 배경 개념

### 2.1 계층형 아키텍처와 의존 방향
- **계층**: 코드를 역할별로 네 칸으로 나눈다.

```text
api          HTTP를 아는 곳. 요청을 받아 DTO로 바꾸고, 결과를 JSON으로 돌려준다.
 ↓
application  "무엇을 할지" 정하는 곳. 트랜잭션을 열고 여러 도메인 규칙을 조립한다.
 ↓
domain       업무 규칙 그 자체. DB도 HTTP도 모른다.
 ↑
infra        DB에 실제로 붙는 곳(JPA Repository, MyBatis Mapper).
```

- **왜 방향이 중요한가**: `domain`이 `infra`를 모르면, DB를 바꿔도 업무 규칙은 그대로다. 반대로 규칙 코드 안에 SQL이 섞이면 무엇 하나 바꿀 때마다 전부 흔들린다.
- **비유**: 식당에서 홀 직원(api), 주방장(application), 레시피(domain), 식자재 창고(infra)를 나눈 것과 같다. 레시피가 "창고 3번 칸"을 직접 가리키면 창고 구조를 바꿀 때 레시피를 다 고쳐야 한다.

### 2.2 JPA와 MyBatis를 함께 쓰는 이유 (가벼운 CQRS)
- **JPA**: 객체를 저장하고 바꾸는 데 강하다. `post.hide()`처럼 객체 상태를 바꾸면 알아서 UPDATE를 만들어준다. 하지만 복잡한 조회는 SQL이 눈에 보이지 않아 성능 문제를 찾기 어렵다.
- **MyBatis**: SQL을 직접 쓴다. 목록·검색·통계처럼 조인과 조건이 복잡한 조회에 유리하고, 결과를 조회 전용 DTO에 바로 담아 N+1 문제가 없다.
- **CQRS(Command Query Responsibility Segregation)**: "바꾸는 일(Command)"과 "읽는 일(Query)"을 나누는 설계다. 여기서는 기술까지 나눴다.

| 하는 일 | 사용 | 이유 |
|---|---|---|
| 저장·수정·삭제 | JPA | 변경 감지, 연관관계, Auditing |
| 목록·검색·통계 | MyBatis | SQL을 직접 보고 튜닝 |

- 둘은 **같은 DataSource와 같은 트랜잭션**을 쓴다. 그래서 "JPA로 저장하고 MyBatis로 조회"가 한 트랜잭션에서 가능하다(단, 저장 직후 조회하려면 `flush()`가 필요하다).

### 2.3 Flyway 마이그레이션
- **무엇인가**: DB 스키마 변경을 `V1__init.sql`, `V2__seed.sql`처럼 번호가 붙은 파일로 관리하고, 애플리케이션이 뜰 때 **아직 적용되지 않은 파일만** 순서대로 실행한다.
- **왜 필요한가**: 스키마를 손으로 고치면 "내 PC DB에는 있는 컬럼이 서버에는 없는" 상황이 생긴다. Flyway는 적용 이력을 `flyway_schema_history` 테이블에 남겨 모든 환경이 같은 상태가 되게 한다.
- **중요한 규칙**: 이미 적용된 파일은 **절대 수정하지 않는다**. 체크섬이 달라져 오류가 난다. 바꾸려면 새 번호 파일을 추가한다.
- **이 프로젝트의 특징**: DB가 둘이라 폴더도 둘이다.

```text
db/migration/postgresql/V1__init.sql
db/migration/mysql/V1__init.sql        ← 같은 번호, 같은 의미, 문법만 다름
```

- `ddl-auto=validate`: JPA가 테이블을 만들지 않고, **엔티티와 실제 스키마가 맞는지 검사만** 한다. 스키마 변경 경로를 Flyway 하나로 묶기 위해서다.

### 2.4 프로필로 DB 전환하기
Spring의 **프로필**은 설정 묶음에 이름을 붙이는 기능이다.

```text
application.yml                  공통 설정
application-local.yml            로컬 개발용 (로그 자세히)
application-db-postgresql.yml    PostgreSQL 접속 정보 + Flyway 경로
application-db-mysql.yml         MySQL 접속 정보 + Flyway 경로
```

실행할 때 `local,db-postgresql`처럼 프로필을 켜면 해당 파일들이 겹쳐 적용된다. DB를 바꾸려면 코드가 아니라 **환경변수 `DB_VENDOR`만** 바꾸면 된다.

### 2.5 ProblemDetail (RFC 9457)
- **무엇인가**: 에러 응답 형식의 표준이다. Spring이 기본 지원한다.
- **왜 필요한가**: 에러 응답 형식이 API마다 다르면 프론트가 매번 다르게 처리해야 한다. 형식을 하나로 고정하면 프론트에 에러 처리 코드를 한 번만 쓴다.

```json
{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "요청한 리소스를 찾을 수 없습니다.",
  "instance": "/api/v1/does-not-exist",
  "code": "COMMON_NOT_FOUND",
  "traceId": "08a48c9002cf451b"
}
```

- `code`는 **기계가 읽는 값**이다. 프론트는 메시지 문자열이 아니라 이 코드로 분기한다. 메시지는 바뀔 수 있지만 코드는 계약이다.

### 2.6 traceId와 MDC
- **문제**: 서버 로그에는 여러 사용자의 요청이 뒤섞여 찍힌다. "이 사용자가 받은 에러"에 해당하는 로그만 골라내기 어렵다.
- **해결**: 요청마다 고유 ID(traceId)를 만들어 그 요청에서 찍히는 **모든 로그에 자동으로 붙인다**. MDC(Mapped Diagnostic Context)는 이 값을 스레드에 매달아두는 슬로트다.
- 에러 응답에도 같은 traceId를 넣으므로, 사용자가 보낸 화면 캡처 하나로 로그를 바로 찾을 수 있다.

### 2.7 ArchUnit
- **무엇인가**: "아키텍처 규칙"을 테스트 코드로 쓰는 라이브러리다. 실제 클래스 파일을 읽어 의존 관계를 검사한다.
- **왜 필요한가**: "컨트롤러에서 Repository를 직접 부르지 말자" 같은 규칙은 코드 리뷰로만 지키면 언젠가 무너진다. 테스트로 만들면 규칙을 어긴 순간 CI가 빨간불을 켠다.

```java
noClasses().that().resideInAPackage("..api..")
    .should().dependOnClassesThat().areAnnotatedWith(Entity.class);
```

### 2.8 ShedLock과 분산 락
- **문제**: 서버를 2대로 늘리면 `@Scheduled` 작업이 **양쪽에서 동시에** 실행된다. 파일 정리 작업이 두 번 돌면 곤란하다.
- **해결**: 작업 전에 DB의 `shedlock` 테이블에 "내가 지금 이 작업을 한다"는 행을 잠근다. 잠금을 못 얻은 인스턴스는 그냥 건너뛴다.
- `usingDbTime()`을 쓰면 서버들의 시계가 조금씩 달라도 DB 시간을 기준으로 판단해 안전하다.

## 3. 따라하기

### 3.1 두 DB용 마이그레이션 작성
PRD 11장의 테이블 정의를 두 벤더 문법으로 옮겼다. 차이나는 부분만 보면 이렇다.

| 항목 | PostgreSQL | MySQL |
|---|---|---|
| 자동 증가 ID | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `BIGINT AUTO_INCREMENT` |
| 시각 | `TIMESTAMP(6) WITH TIME ZONE` | `DATETIME(6)` |
| 불리언 | `BOOLEAN` | `TINYINT(1)` |
| 긴 텍스트 | `TEXT` | `LONGTEXT` |
| 인덱스 선언 | 테이블 밖 `CREATE INDEX` | 테이블 안 `INDEX ...` |
| 현재 시각 | `NOW()` | `UTC_TIMESTAMP(6)` |

```sql
-- postgresql/V1__init.sql (일부)
CREATE TABLE posts (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    content    TEXT NOT NULL,
    created_at TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    ...
);
CREATE INDEX idx_posts_board_list ON posts (board_id, deleted_at, status, is_notice, created_at);
```

```sql
-- mysql/V1__init.sql (같은 테이블)
CREATE TABLE posts (
    id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    content    LONGTEXT NOT NULL,
    created_at DATETIME(6) NOT NULL,
    ...
    INDEX idx_posts_board_list (board_id, deleted_at, status, is_notice, created_at)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci;
```

### 3.2 MyBatis 벤더 분기 설정

```java
@Bean
public DatabaseIdProvider databaseIdProvider() {
    VendorDatabaseIdProvider provider = new VendorDatabaseIdProvider();
    Properties properties = new Properties();
    properties.setProperty("PostgreSQL", "postgresql");  // JDBC 드라이버가 알려주는 제품명 → 별칭
    properties.setProperty("MySQL", "mysql");
    provider.setProperties(properties);
    return provider;
}
```

이렇게 해두면 XML에서 DB마다 다른 SQL을 쓸 수 있다.

```xml
<select id="currentVendor" resultType="string" databaseId="postgresql">
    SELECT CAST('postgresql' AS VARCHAR)
</select>
<select id="currentVendor" resultType="string" databaseId="mysql">
    SELECT 'mysql' FROM DUAL
</select>

<!-- databaseId가 없으면 두 DB 공통으로 쓰인다 -->
<select id="countBoards" resultType="long">
    SELECT COUNT(*) FROM boards
</select>
```

**원칙**: 대부분은 표준 SQL로 쓰고, 정말 다른 구문(upsert, 날짜 함수 등)만 분기한다. 분기가 늘수록 유지보수가 어려워진다.

### 3.3 공통 에러 처리

```java
// 1) 도메인별 enum이 구현할 인터페이스
public interface ErrorCode {
    HttpStatus getStatus();
    String getCode();
    String getMessage();
}

// 2) 서비스에서 던지는 예외
throw new BusinessException(CommonErrorCode.NOT_FOUND);

// 3) 한 곳에서 ProblemDetail로 변환
@ExceptionHandler(BusinessException.class)
public ProblemDetail handleBusiness(BusinessException e, HttpServletRequest request) {
    ErrorCode code = e.getErrorCode();
    return problem(code.getStatus(), code.getCode(), e.getMessage(), request);
}
```

처리하지 못한 예외(`Exception`)는 500으로 응답하되 **내부 메시지를 노출하지 않고** 로그에만 남긴다. 스택 트레이스에 DB 구조나 파일 경로가 드러날 수 있기 때문이다.

### 3.4 요청 추적 필터

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)   // 가장 먼저 실행되어야 이후 로그에 ID가 붙는다
public class TraceIdFilter extends OncePerRequestFilter {
    protected void doFilterInternal(...) {
        String traceId = request.getHeader("X-Request-Id");
        if (traceId == null || traceId.isBlank()) {
            traceId = UUID.randomUUID().toString().replace("-", "").substring(0, 16);
        }
        MDC.put(TRACE_ID, traceId);
        response.setHeader("X-Request-Id", traceId);
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.remove(TRACE_ID);   // 스레드 재사용 때문에 반드시 지운다
        }
    }
}
```

`finally`에서 `MDC.remove`를 빠뜨리면, 스레드가 재사용될 때 **다음 요청 로그에 남의 traceId**가 찍힌다. 흔한 실수다.

### 3.5 테스트: 하나의 코드로 두 DB 검증

```java
@SpringBootTest
@ActiveProfiles(resolver = DbVendorProfileResolver.class)   // test + db-<벤더>
public abstract class IntegrationTestSupport {

    private static final JdbcDatabaseContainer CONTAINER = createContainer();
    static { CONTAINER.start(); }    // JVM당 한 번만 띄워 재사용

    private static JdbcDatabaseContainer createContainer() {
        if (DbVendor.isMysql()) {
            return new MySQLContainer(DockerImageName.parse("mysql:8.4"));
        }
        return new PostgreSQLContainer(DockerImageName.parse("postgres:17-alpine"));
    }

    @DynamicPropertySource
    static void datasourceProperties(DynamicPropertyRegistry registry) {
        registry.add("DB_HOST", CONTAINER::getHost);
        registry.add("DB_PORT", () -> CONTAINER.getMappedPort(DbVendor.isMysql() ? 3306 : 5432));
        ...
    }
}
```

**Testcontainers**는 테스트가 시작될 때 진짜 DB를 도커로 띄우고 끝나면 정리한다. H2 같은 가짜 DB로 테스트하면 문법 차이 때문에 "테스트는 통과하는데 운영에서 깨지는" 일이 생기므로, 실제 DB로 테스트한다.

## 4. 결정과 이유

| 결정 | 고려한 대안 | 선택 이유 |
|---|---|---|
| Flyway 폴더를 벤더별로 분리 | 한 폴더에 조건부 SQL | 파일마다 문법이 다르므로 섞으면 읽기 어렵다. 폴더를 나누면 "두 파일을 함께 고친다"는 규칙만 지키면 된다. |
| `ddl-auto=validate` | `update` | `update`는 운영에서 예측 못 한 스키마 변경을 만든다. 스키마 변경 경로를 Flyway 하나로 고정한다. |
| 테스트에 Testcontainers | H2 인메모리 DB | H2는 두 DB 중 어느 것도 아니다. 벤더 차이를 검증하는 것이 이 프로젝트의 핵심이라 실제 DB가 필요하다. |
| 컨테이너를 JVM당 1회 기동 | 테스트 클래스마다 기동 | 기동에 수 초가 걸려 테스트가 크게 느려진다. |
| `@ActiveProfiles(resolver=...)` | 테스트마다 프로필 하드코딩 | `-PdbVendor` 하나로 전체 테스트의 대상 DB를 바꾸기 위해서다. |
| ShedLock `usingDbTime()` | 서버 시계 사용 | 인스턴스 간 시계 차이로 락이 겹치는 것을 막는다. |
| 캐시는 Caffeine(로컬) | 처음부터 Redis | Redis는 운영 부담이 늘어난다. Spring Cache 추상화를 쓰면 나중에 교체해도 서비스 코드는 그대로다. |

## 5. 겪은 문제와 해결

### 문제 1: Spring Boot 4에서 `@AutoConfigureMockMvc`를 못 찾음
```text
error: package org.springframework.boot.test.autoconfigure.web.servlet does not exist
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
```
- **원인**: Boot 4에서 테스트 자동설정이 모듈별로 재배치되었다. MockMvc 관련은 `spring-boot-webmvc-test` 모듈의 `org.springframework.boot.webmvc.test.autoconfigure` 패키지로 옮겨졌다.
- **찾은 방법**: Gradle 캐시의 jar 안을 직접 뒤졌다.

```bash
python -c "
import zipfile
z = zipfile.ZipFile(r'...\spring-boot-webmvc-test-4.1.1.jar')
print([n for n in z.namelist() if 'AutoConfigureMockMvc' in n])"
```
- **해결**: import 경로를 `org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc`로 바꿨다.
- **배운 점**: 메이저 버전이 올라가면 인터넷 예제의 import가 그대로 맞지 않을 수 있다. 라이브러리 jar가 정답을 갖고 있다.

### 문제 2: 없는 경로 요청이 404가 아니라 500
```text
Status expected:<404> but was:<500>
ERROR c.e.t.g.e.GlobalExceptionHandler - unexpected error
org.springframework.web.servlet.NoHandlerFoundException: No endpoint GET /api/v1/does-not-exist.
```
- **원인**: `NoResourceFoundException`만 처리하도록 만들었는데, 정적 리소스 매핑을 끈 상태에서는 `NoHandlerFoundException`이 던져진다. 그래서 "처리 못 한 예외"로 떨어져 500이 되었다.
- **해결**: 두 예외를 함께 처리하도록 바꿨다.

```java
@ExceptionHandler({NoResourceFoundException.class, NoHandlerFoundException.class})
public ProblemDetail handleNoResource(Exception e, HttpServletRequest request) { ... }
```
- **배운 점**: 전역 예외 처리는 "무엇을 잡는가"보다 **무엇이 안 잡혀서 500으로 새는가**를 확인해야 한다. 500 로그를 남겨둔 덕분에 바로 찾았다.

### 문제 3: ArchUnit이 "빈 계층"을 위반으로 판정
```text
Architecture Violation - Rule 'Layered architecture ...' was violated (4 times):
Layer 'api' is empty
Layer 'application' is empty
```
- **원인**: M1에는 아직 도메인 코드가 없어 네 계층이 모두 비어 있는데, ArchUnit은 기본적으로 빈 계층을 설정 실수로 본다.
- **해결**: `.withOptionalLayers(true)`를 추가했다. 도메인이 생기면 규칙은 그대로 동작한다.

### 문제 4 (확인 절차): 규칙이 진짜 동작하는지 검증
테스트가 통과하는 것만으로는 "규칙이 동작한다"고 말할 수 없다. 검사 대상이 없어서 통과했을 수도 있기 때문이다. 그래서 **일부러 규칙을 어긴 클래스**를 넣고 실패를 확인했다.

```java
@Component
public class ArchViolationSample {
    @Autowired
    private String violatesFieldInjectionRule;   // ARCH-06 위반
}
```

```text
ARCH-06: 필드 주입(@Autowired 필드)을 쓰지 않는다 FAILED
  Field <...ArchViolationSample.violatesFieldInjectionRule> is annotated with @Autowired
```

확인 후 샘플 클래스는 삭제했다.

## 7. 회고와 다음 단계

**잘된 점**
- 같은 테스트 코드가 두 DB에서 모두 통과한다. DB 이식성을 "주장"이 아니라 "검증된 사실"로 만들었다.
- ArchUnit 규칙이 실제로 위반을 잡는지 확인까지 했다. 규칙은 만들었는데 동작하지 않는 상태가 가장 위험하다.
- 에러 형식을 지금 고정해두어, 앞으로 만드는 모든 API가 자동으로 같은 형식을 따른다.

**아쉬운 점 / 개선할 점**
- 테스트가 두 DB를 각각 돌리면 컨테이너 기동 때문에 시간이 걸린다(각 40초 내외). CI에서는 매트릭스로 병렬 실행할 예정이다.
- rate limiter가 인스턴스별 인메모리라 서버를 늘리면 한도가 인스턴스 수만큼 늘어난다. 한계를 문서에 적어뒀고, 필요해지면 Redis 구현으로 교체한다.
- `AuditorAware`가 아직 빈 값을 반환한다. M2에서 로그인 사용자 id를 반환하도록 바꾼다.

**다음 단계 (M2)**
- users, refresh_tokens 엔티티와 JWT 인증
- 회원가입/로그인/재발급(rotation)/로그아웃
- 초기 관리자 계정 생성, 로그인 시도 제한
